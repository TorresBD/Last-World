## Processes and protocol

The default suite retains the six campaign/ground/movement-Vulkan/movement-DX12/river-render/campaign-render baseline phases. In addition, it runs both Windows test binaries with `--list`, compares actual names with `benchmark-unit-tests.json`, then schedules each actual test in its own process with `--exact NAME --test-threads 1 --nocapture`. Host-expected names are a prediction, not Windows execution evidence. Inventory drift is retained. Exactly one passed/zero failed/zero ignored test and its exact named execution line are required; a zero/other-test exit0 cannot pass. Commands are reconstructed from verified definitions and actual inventory when resuming, rather than trusting persisted arguments. Discovery failure gets two attempts and marks only that binary's unverified cases skipped; other binaries and stress cases continue.

Native cases use `Last-World.exe --benchmark-case ID --benchmark-output check-results/RUN_ID/benchmark`, plus the optional planned backend. Every attempt has separate supervisor stdout/stderr files. Native artifacts use `ID-PID-started_ms-report.json` and matching progress/session identity. A native result passes only after exit0, no native fatal tags, exact case/PID/session/time/attempt agreement, `status=passed`, boolean `passed=true` and boolean `checkpoint.committed=true`. Window core-only or pending-render results cannot pass.

Benchmark children receive `LAST_WORLD_BENCHMARK_ATTEMPT=1` or `2` in a separate sorted, Unicode, NUL-terminated Win32 environment block. Unit/discovery/baseline children have this variable absent. Each child receives its own owned TEMP/TMP directory; the parent environment is never modified. Attempt2 restores the true prephase state and reruns simulation plus any required rendering/capture validation. The supervisor rejects a receipt-only recovery result on attempt2, so a GPU error or crash during teardown cannot be hidden by a prior commit.

External failures are projected atomically into the small `benchmark/rejected-attempts.json` marker before retry/continuation, including interrupted-attempt recovery. Entries match `case_id`, `attempt_index` and the exact native-source/executable SHA256 pair. Native code owns rollback/save loading and promotes the matching true prephase `.previous` state before replay. PS never parses or edits simulation saves. A rejected attempt1 does not reject a later successful attempt2; a separately rejected attempt2 also prevents the next different case from adopting its failed checkpoint. The adjacent frozen native build stamp and rejection marker are included in feedback.

The plan includes explicit recovery-control probes that abort after commit: one crashes only attempt1, one always crashes, and a following case checks continuation from valid prephase state. The always-crashing control is intentionally recorded skipped after two failures, with raw errors retained; it never becomes a pass. Consequently a complete control suite can terminate as completed-with-failures even when that expected rejection/recovery behavior worked. These probes test the harness and do not qualify gameplay/FPS.

Requested-rate completion and rate sustained are separate. A correct finished phase can report that100× was not sustained, along with debt, achieved simulation speed, frame/memory counters and limits. Neither supervisor completion nor successful individual tests is a60FPS,20km, all160-trait or complete mandatory-biology claim. The coverage inventory documents what is and is not exercised.

## Durable retry and resume

`check-results/current-suite.json` points to the authoritative per-run `suite-journal.json`. Writes use a flushed temporary file and atomic replacement with one `.previous` snapshot. Invalid current JSON can recover the verified previous JSON while preserving the corrupt file. The journal records source/executable/plan/catalogue identities, stable phase order, arguments, attempt count, status, stdout/stderr locations, PID, exact process creation ticks/path/hash, deadline, memory samples and final reasons. It is saved before launch, again while the owned child is suspended, and after the result.

Same-build reruns retain completed/skipped phases and resume only unfinished work. Native successful checkpoints remain beneath the shared run root; failed work does not replace a last-good checkpoint. Each phase gets at most two attempts total, including interrupted attempts. After two failures it becomes `skipped_after_failures` with its actual final reason, and later phases continue. It is never relabelled passed. A new executable/native-content/plan/test-catalogue identity starts a new suite and retains earlier run folders.

`Run-Checks-OwnedProcess.ps1` uses standard Windows/.NET APIs. It creates a child suspended, attaches it to an owned Job Object, journals ownership, then resumes it. Job close kills its own children if the supervisor dies; child fault dialogs are suppressed. The CMD watchdog permits at most two unexpected supervisor restarts. Exit0 is completed/passed;10 is completed with failures/skips;11 is uncertain cleanup;12 is preparation/protocol failure;2 is another active supervisor. These terminal dispositions never trigger a restart loop.

Recovery may terminate only a journal-owned PID whose creation time, exact executable path and executable hash all match. Reused PIDs and unrelated programs are not killed. If a launch interrupted before ownership could be recorded, a matching unowned process makes cleanup uncertain; further launches stop and diagnostics are bundled. This deliberately avoids guessing. Host events are retained separately during native execution and merged into append-only console history only after owned children have exited and no same-install native program is active.

## Safety limits and return file

The per-process memory budget is `min(6GiB,25% of OS-visible physical RAM)`. A Windows Job Object enforces the commit limit; one-second polling records working/private counters and labels observed guard stops. A native allocation failure under that enforced cap may still be a native failure; the suite does not seek a whole-machine OOM or claim that polling is a precise peak-memory/VRAM measurement. GPU WMI AdapterRAM is explicitly labelled as a potentially truncated32-bit field. Counts and gameplay rules are not secretly reduced to fit the guard.

Baselines retain their bounded deadlines: CPU campaign600seconds, campaign window240seconds, ground/river180seconds each and isolated movement120seconds/backend. Native-case deadlines come from the single plan; discovered unit cases use their catalogue deadline or180seconds. Deadline enforcement and polling use monotonic Stopwatch elapsed time; UTC is retained only for artifact identity and timestamps, so a backward clock correction cannot extend a phase. These are functional supervision limits, not performance acceptance thresholds.

The final ZIP contains owned run journals, attempts, native reports/progress, fresh captures, optional owned dump files when present, sampled memory, host/source identity and append-only histories. Native checkpoint directories, save files, previous feedback ZIPs and unrelated player files are excluded. Other owned files over64MiB remain local with explicit exclusion notes. `feedback-bundle-notes.json` records exclusions/warnings. Checkpoints and all underlying logs stay local for resume; replacing the feedback archive does not delete them.

## Per-attempt CPU, RAM and GPU telemetry

`Run-Checks-GpuTelemetry.ps1` adds optional read-only sampling alongside the existing one-second owned-process memory poll. Every native game attempt, including CPU-only workloads, records process CPU time/utilization, system CPU utilization and system RAM/commit availability in `cases/PHASE/attempt-N-hardware.jsonl`. GPU movement/render baselines and native window cases additionally query WDDM GPU Engine utilization and GPU Process Memory dedicated/shared usage. Units/discovery retain their existing process-memory records without hardware-query setup. The original process working-set/private-byte samples and peaks remain in host history/journal, identified by the same owner. System RAM and system CPU include other programs; they are not attributed entirely to the game.

CPU process utilization is reported both with100% meaning one logical processor and divided by `Environment.ProcessorCount` for its reported logical-capacity percentage. The first delta is null/warmup; CPU time and elapsed time remain paired across unavailable reads. System CPU uses `GetSystemTimes` with idle subtracted once from kernel+user. Its documented processor-group limitation above64logical processors is retained in the schema. `GlobalMemoryStatusEx` reports total/available/used physical bytes and effective total/available commit limits. Commit fields are not disk page-file sizes or VRAM. CPU model and OS-reported topology remain in the one-time host identity record.

GPU queries use `PdhAddEnglishCounterW` to localize English wildcard paths, `PdhGetCounterInfoW` to recover those localized paths, and the documented wildcard `PdhAddCounterW` plus formatted-array read. Both query paths and each returned instance must match the owned PID, while each sample checks the retained process handle and exact creation ticks against the journaled path/hash owner. Per-instance engine names, adapter LUID/physical indices, valid-data status and values are retained. Host GPU names/drivers remain in host metadata; a LUID is not guessed to match an ambiguous WMI adapter name. Rate counters need warmup; failed query collection prevents old data from being read as a fresh sample. Counter setup errors, unsupported/missing instances, invalid statuses and first-rate samples produce explicit status plus null values. An actual valid zero remains zero.

The GPU summary reports the maximum engine utilization, separate3D/Compute/Copy maxima/counts and dedicated/shared process-byte totals across reported instances. Engine percentages are never summed into an invented whole-GPU percentage. Dedicated process allocations are not whole-adapter physical VRAM/residency, and shared allocations/known WDDM counter defects limit interpretation. Memory PDH reads explicitly disable default scaling and100% capping. No NVIDIA utility, administrative access or driver changes are required.

Each counter read is capped at1MiB/512instances; handles/buffers are disposed. GPU collection exceeding250ms disables later GPU reads for that attempt while preserving CPU/RAM sampling. The synchronous PDH call itself cannot safely be interrupted; its elapsed cost is reported. Preparation, per-sample collection/format/write wall time and supervisor-process CPU time over sampling intervals are recorded separately from native frame timings, with CPU timer resolution limitations. JSONL rotates into8MiB segments without discarding prior records, so every segment remains below the feedback single-file limit and is recursively included. The per-attempt atomic hardware summary lists segment names, sample/valid-data counts, metric extrema, unavailable errors and overhead. The first serialized row is round-tripped through a schema/owner probe; GPU attempts also validate native interop layout before querying. Missing instrumentation does not convert a child failure into a pass or stop later gameplay tests.

These additions have host model/static checks; Windows PDH/Win32/PowerShell execution remains untested here. Current-build returned PC hardware samples are required before reporting actual GPU3D/Compute utilization, VRAM allocation, CPU pressure or RAM availability. Primary references: [English counter localization](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhaddenglishcounterw), [wildcard counter reads](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetformattedcounterarrayw), [PDH validity/scaling](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetformattedcountervalue), [WDDM GPU/engine semantics](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/), [process-memory counter limitation](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value), [system CPU](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes), [system memory](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex).
